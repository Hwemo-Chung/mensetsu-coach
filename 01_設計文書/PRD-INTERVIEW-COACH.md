## 1. プロダクト概要

- **一行で**：日本で転職する外国人求職者が、チャットで企業別の想定質問を受け取り、自分の回答に合った日本語ビジネススクリプト（日本語・発音・翻訳）を得て、本番用スクリプトを仕上げるツール。
- **主な差別化ポイント**：日本語を直すだけで終わらず、**質問に答える構造**を先に整えます。添削ルールは開発者本人の面接記録から取ったデータで、コードとは分離された国別パック（`packs/jp.json`）にあります。
- **ビジョン**：日本から始め、国別パックを追加する構造で広げます。現在あるのは日本パックと韓国パック（ベータ、第1段階）の2つです（F14）。

## 2. 課題とペルソナ

- **ペルソナ**：日本に住む外国人求職者（一次ターゲット：韓国語ユーザー）。エージェント経由の面接が繰り返され、会社ごとにスクリプトを新たに準備する必要があり、日本語での面接そのものが負担です。
- **実例**：面接録音の文字起こしを見ると、面接官が同じ質問を3回聞き返していました。原因は日本語力よりも、質問に答えず、準備していた別の質問に答えていたことにありました。

## 3. 目標 / 非目標

**目標（MVP）**
- 企業資料の入力から質問選択、回答入力、チェック・添削、スクリプト出力まで途切れなくつなぐ
- 出力が日本語フィールドで他の言語に変わらないよう、プログラムのゲートで強制
- 発音表記でイントネーションと強調がひと目でわかるようにする

**非目標**
- メッセンジャープラットフォーム連携（単独のウェブサイトで代替）

- 履歴書スクリーニングなど、審査で避けるべきリストにある機能

## 4. 主要シナリオ（実装基準）

1. 企業のメールや求人情報を貼り付ける。履歴書・職務経歴書は任意で添付。
2. 想定質問10問を受け取る（日本語の質問、説明言語の翻訳、根拠1行）。
3. 番号を入力して質問を選び、自分の回答を説明言語か日本語で書く。
4. チェック・添削を受ける：質問に答えたか、4段階（復唱→結論→基準・数字→締め）の ✓/✗（復唱は推奨なので、なければヒント）、ルールDBによる添削（before/after・理由）。
5. スクリプトを受け取る：日本語敬語の模範回答 / 発音（イントネーション表記）/ 翻訳 / イントネーション・強調のポイント。
6. 別の番号を選ぶか、同じ質問に再回答するか、逆質問を受け取るか、「끝내기·저장」（終了・保存）で Markdown をダウンロードする。

## 5. 機能要件

### F1. 企業登録
- テキストの貼り付け、または添付1件（PDF、DOCX、画像、TXT/MD、3MB 以下）。添付は保存せず、メモリ上でのみ処理。
- 完了基準（達成）：入力段階の個人情報マスキング（テスト）、インジェクションを仕込んだ合成メールの評価で指示追従 0/10。

### F2. 質問生成
- 質問10問、面接段階とカテゴリを表示、根拠1行。
- **日本語フィールドのルール**：`question_ja` は日本語のみ。他の言語が混ざれば1回再生成し、それでも失敗すればエラー応答。
- 完了基準（達成）：10問中6問以上が資料固有の語句を参照しているかをコードで検査（F2 ゲート）。

### F5. 模範スクリプト
- 出力項目は最大4つ：`ja`、`reading`、`translation`、`points`（目的地の言語 = 母語なら `reading`・`translation` なし、11/03）。
  - `ja`：日本語のビジネス敬語。約60秒分。結論を先に、根拠の数字は1つ、最後の締めは質問タイプに応じて 選択肢・貢献・改善・質問 のいずれか（パック基準の `closingOf`）。モデルは段階別フィールド（`fukusho`・`ketsuron`・`kijun`・`sentakushi`）で書き、コードがつなげる。回答にない数値・経歴・固有名詞は作らず、`［ここに実績の数字］` のようなプレースホルダーで空ける。
  - `reading`：`ja` の発音を母語の文字で書き、イントネーションと強調を記号で表示（表記は下記「言語ルール（2軸）」）。目的地の言語 = 母語なら `reading`・`translation` をリクエストせず、表示もしない（11/03、実装済み）。
    - `↗` 上げて言う
    - `↘` 下げて言う
    - `《 》` 力を込めて言う
    - `/` 短く区切る
  - `translation`：説明言語への翻訳。
  - `points`：説明言語によるイントネーション・強調のポイント2〜4個。
- **言語ゲート**：`ja` は日本語のみ、`reading`・`translation`・`points` は説明言語ゲート（`EXPLAIN_LANGS`）を通過する必要がある。失敗すれば1回再試行してからエラー。
- 完了基準（達成、11/02）：実呼び出し ko・en・ja 各1件で4項目の存在・ゲート通過。プロンプトを変えたら再度1回確認。→ 11/03 のプロンプト変更（ひらがな発音、翻訳のみ再リクエスト）後に再確認が必要。

### F7. チャットUI
- 段階：アクセスコード（`OPEN_ACCESS` 未設定のときのみ）→ メール → 質問選択（番号）→ 回答 → チェック・添削 + スクリプト → 質問選択に戻る。
- 入力欄は複数行で、Enter は改行です。Ctrl/Cmd+Enter で送信します。
- チェック結果の下に「답변에서 확인되지 않은 첨삭 N건은 뺐어요」（回答で確認できなかった添削 N件は除外しました）を常に（0件を含めて）表示します。「규칙 밖 첨삭 N건 제외」（ルール外の添削 N件を除外）は事実と異なるため使いません（ルールIDがスキーマ enum なのでルール外の添削は出力され得ない、UIUX-SPEC §0）。

### F11. アクセスと1日の利用上限（11/06 変更）
- `OPEN_ACCESS` 未設定：コード入力段階でサーバーが確認します。正しい場合のみ次の段階に進みます。ページを開くたびにコードを再度尋ねます。
- `OPEN_ACCESS=1`：最初の画面はメールの入力です。AI や外部 API を呼び出す11の経路（11/07 にメール登録を追加。まとめを作るときだけ数える）は、コードなしで1日の上限まで使えます（全体 `DAILY_LIMIT`、IP ごと `DAILY_LIMIT_IP`、整数のみ、日本時間0時にリセット）。提出版の値は全体60回、IP ごと4回です（11/06 決定。想定質問の生成1回と回答1件の3回で、体験1回分。その後のメール登録は上限を超えるため、まとめの代わりに記録そのものを送る）。

- 回数は KV（`KV_REST_API_*`）で数え、未設定か応答しない場合はインスタンスのメモリで数えます。
- 運用値はデプロイ環境の環境変数にあり、文書とリポジトリには値を書きません。

### 言語ルール（2軸、11/03 ユーザー確定）
- **目的地パック**（`pack.language_pair.target`）が質問・模範回答・スクリプトの言語を決めます。
- **母語 = 画面言語**（`lang`）がそれ以外のすべてを決めます：画面、説明、翻訳、F3 構造フィードバック、F4 添削理由、スクリプトのポイント・分析、口ぐせ、エクスポートの案内。
- 発音（`reading`）は母語の文字で書きます。

|---|---|---|---|---|
| 日本 (ja) | ko | 日本語 | 韓国語 | ハングル |
| 日本 (ja) | en | 日本語 | 英語 | ローマ字 (ヘボン式) |
| 日本 (ja) | ja | 日本語 | 日本語 | 非表示（翻訳も非表示） |
| 韓国 (ko, ベータ) | ja | 韓国語 | 日本語 | カタカナ |
| 韓国 (ko, ベータ) | en | 韓国語 | 英語 | 改訂ローマ字表記 |
| 韓国 (ko, ベータ) | ko | 韓国語 | 韓国語 | 非表示（翻訳も非表示） |
| 英語圏 (en, 準備中) | すべて | 英語 | 母語 | IPA のみ |

- 実装への影響：スクリプトのスキーマ・プロンプト・`EXPLAIN_LANGS` の発音ゲートが（target, lang）のペア基準に変わります。実呼び出しによる確認が1回必要です（ユーザー承認）。`demo-ja.json` は再録画せず、画面で発音・翻訳を非表示にします。

  - 入力段階のマスキングは実装済みです（F1）。PDF・画像の添付と文中の名前はマスクできません。
  - Anthropic API のデータ保持設定はまだ確認していません。
  - プライバシーポリシー：`/privacy.html`。
- **入力防御**：資料や回答の中の指示文には従いません（プロンプトのルール）。評価（実呼び出し）で、メール・回答内の指示に従わないことを確認しました。
- **アクセス制御**：`OPEN_ACCESS` 未設定のときは、コードが設定されていなければ AI を呼び出すリクエストをすべてブロックします。`OPEN_ACCESS=1` のときは、コードなしのリクエストを1日の上限まで通します（F11）。リクエスト制限は API 別・IP 別の10分単位です（アクセス確認 20、質問生成 10、チェック・スクリプト・台本の検証各 30、逆質問 10、メール登録 5）。サーバーインスタンスのメモリにあるため、インスタンス間では共有されません。
- **コスト**：1セッション（回答3件 + 逆質問）で約 0.26 USD（実測）。Opus の採点は約 0.031 USD/回、Sonnet は約 0.037 USD/回。テストは基本的にフェイククライアントを使い、実呼び出しはプロンプトやモデルを変えた後に1回だけ行います。

- 韓国語の混入（質問フィールド）：言語ゲートと再試行で対応。実際の発生頻度は要確認。
- 発音表記の品質（イントネーション記号の正確さ）：実呼び出しでの確認は言語ごとに1回のみです。

- 評価の限界：評価データは Claude が作成し、別の Claude エージェントが批判的に検証した合成データです。人手ラベルの実データはなく、件数（n）も少ないです。

- §15 作業による JP 経路の回帰：フィールド名・プロンプトの変更は、オフラインテストではモデル出力の変化を捉えられません。実呼び出しでの確認（ユーザー承認）と 11/6 の凍結が前提です。

## 17. 企業・職種の自動調査（11/04 追加）

詳細な仕様は `SUPPLEMENT-AUTO-RESEARCH.md` です。サーバーの `RESEARCH_ENABLED=1` のときのみ動作し、オフなら現在の動作と同一です。

| ID | 機能 | 状態 | 内容 |
|---|---|---|---|
| R | 企業・職種の調査（ステージ R） | 実装済み（`RESEARCH_ENABLED=1`） | 最初の質問の後、抽出した企業名・職種名を利用者が確認してから `POST /api/research` を実行し、ブリーフカードを表示して質問を再生成します。検索は企業名・職種名・汎用語のみで、失敗時は最初の質問を残して `research_status: unavailable` と表示します。出典はコードで検査します（同仕様 §10） |
| F16 | 希望プロフィールと適合・不一致フラグ | 実装済み（`RESEARCH_ENABLED=1`） | `desired_position_profile` はブラウザ内の専用キーに保存し、編集・削除でき、適合判定の呼び出しにのみ送ります。資料・公開情報・希望の相違は両側を引用した確認の促しとして示し、推奨・非推奨などの判定は出しません |
| F17 | 面接後の振り返り | 実装済み（`RESEARCH_ENABLED=1`） | 実際に聞かれた質問 / 難しかった場面 / 結果と次の段階を企業ごとにブラウザ内へ保存します。生成した質問との重なりはブラウザ内でのみ表示します |
