1概要

日本で転職する人のための面接コーチです。求人やエージェントのメールを貼ると、その会社専用の想定質問を10問作ります。質問を選んで答えると、構成のチェック、ルールに基づく日本語の添削、模範スクリプト（約60秒。日本語・読み方・訳・イントネーション）を返します。

自律エージェントではなく、Messages API 上のワークフローです。段階の間にプログラムのゲートを置き、モデルの自己申告をそのまま信じません。

求人メール・履歴書→想定質問10問→回答→構成チェック・添削→模範スクリプト→面接準備資料・まとめメール
10問会社専用の想定質問（10問中6問以上が資料の語句を含むことをコードで確認）
21件日本語添削のルールDB（ルールIDをスキーマの enum で固定）
3種Claude のモデル（Sonnet 5.5 で生成、Opus 5.5 で採点、Haiku 5.5 で調査）

2ワークフロー

カードを押すと詳細、▶ 実行で各段階の状態（待機 → 実行中 → 通過・失敗・停止）を再生します。失敗の設定は、公開コミット 0925a35・828f3ac で直した「説明言語でないと 502」の事例です。数値は例示で、実測ではありません。操作: ホイールで拡大、ドラッグで移動、F で全体表示、G で簡易表示。

3モデルと役割

段階モデル選んだ理由・設計
想定質問10問claude-sonnet-5-5構造化出力。会社固有性はコードのゲートで確認
構成チェック＋添削claude-opus-5-5生成とは別の呼び出し。作ったモデルが自分の答えを採点しないため
模範スクリプト・逆質問claude-sonnet-5-5説明言語の検査に通らなければ1回だけ再生成
企業・職種の調査claude-haiku-5-5費用を抑えるため。基本版の web_search_20250305・web_fetch_20250910 を使用（新しい版は Haiku との組み合わせで検索が0回だった）
調査結果との比較claude-sonnet-5-5ツールなし。応募者の資料が検索語に入る余地をなくすため
台本・模範スクリプトの照合claude-sonnet-5-5ツールなし。根拠が見つからない文だけを挙げ、文の実在はコードで確認
面接準備資料claude-sonnet-5-5節のまとまりごとに並列で呼び出す。会社の事実・固定の文・空欄の集計はコードが組み立てる
練習のまとめメールclaude-sonnet-5-5失敗・上限超過のときは記録をそのまま送る
模範スクリプトの読み上げgemini-3.8-flash-lite-tts使えない場合は端末の音声
音声での回答Whisper-small（ブラウザ内）録音を端末の外に出さず、フィラーを残す

想定質問・構成チェック＋添削・模範スクリプト・逆質問・面接準備資料は fallbacks: "default"（server-side fallback、ベータ）を指定しています。MCP はアプリに組み込んでいません。開発では、実際のブラウザでの確認に MCP の Claude in Chrome を、デプロイの確認に Vercel の MCP を一部で使いました。

4コードのゲート

  • 入力のマスキング — メール・電話・郵便番号・宛名行を Claude に送る前に伏せる。貼り付けた資料の中の指示には従わない
  • 会社固有性 — 10問中6問以上が資料の語句を含む（一般語は数えない）
  • 調査の出典 — 検索・取得の結果に実在する URL を引用し、同じ企業と確認できた出典だけを数える
  • 添削の引用 — 回答にない箇所を引用した添削は捨てる。語彙ルール16個は引用箇所の表現もコードで確認
  • 説明言語 — 日本語欄が日本語でなければ1回だけ再生成し、2回目も失敗すればエラーを返す
  • 数字 — 模範スクリプトの数字は回答・質問・資料にある数と一致するものだけ。なければ［空欄］
  • 面接準備資料 — 数字と単位、肩書きを履歴書と質問に照合し、照合できない文は「要本人確認」に集める

6Claude Code での開発

Claude Code を開発の中心に置き、プロジェクトの規則は CLAUDE.md にまとめて毎回の作業で読み込ませました。大きな作業は Workflow（サブエージェントの編成）で進め、エージェントが作ったものを別のエージェントが反証する形にしています。

大会前の構想（10/28）は作者が行い、大会期間中の調査・設計・実装・攻撃によるテスト・評価・デモ動画の制作・提出フォームの入力は Claude Code が担いました。作者は判断とフィードバックに徹しました。作者の指示318件に対して、Claude Code のツール呼び出しは15,799回、サブエージェントは638です（11/07 22:49 時点のセッション記録の集計）。工程の流れは 開発工程（全画面）、証拠は 01_設計文書/dev-notes/PROCESS-EVIDENCE.md にあります。

公開前のスキャンは git の pre-push フックでも動き、Claude Code を通さない git push でも同じ検査をします。

開発の進め方

  1. 復唱 — 着手前に、何を・どこに・完了基準を言い直して認識を合わせる
  2. ASCII モックアップ — 画面は実装前に記号で確認し、作り直しを減らす
  3. PRD → TDD — 目標・範囲・完了基準を決め、失敗するテストを書いてから実装する
  4. データ収集 — 公開資料の調査は Sonnet の複数エージェントに分け、別のエージェントが検証する。同時実行は10体まで
  5. スクリーンショットと動画での確認 — ブラウザの回帰テストが画面を撮影し、サブエージェントがアプリとデモを攻撃する
  6. 公開 — push の前に個人情報と秘密情報をスキャンする（/publish-check）
  7. 使用量の管理 — コンテキスト・5時間枠・週間枠の使用率と費用を見ながら作業し、RTK と TokenEconomizer でトークンの消費を抑える

攻撃レビューで見つけて直した例

DOCX の圧縮爆弾の検査回避、数字ゲートの部分一致（「2015年」があると「15%」が通る）、誤入力が続くと正しいアクセスコードまで拒否される問題。報告はそのまま信じず、手元で再現できたものだけを、失敗するテストを先に書いて修正しました。

制約

  • 評価データは Claude が作り、別の Claude エージェントが反証チェックしたもの。口語の回答では質問とのずれを見逃す例がある
  • 構成チェックはモデルの判定で、判定と説明が食い違うことがある
  • PDF・画像の添付はマスクしない。履歴書の氏名・住所などは本文のまま AI に送られる
  • 提出版は審査と試用のための構成。実運用前に必要な修正は README の「実運用前に修正が必要な点」に記載
