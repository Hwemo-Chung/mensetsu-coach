# 補足仕様 — 企業・職種の自動調査、スクリプト支援、面接の振り返り

位置づけ：`PRD-INTERVIEW-COACH.md` と `dev-notes/HARDENING-REVIEW.md` の補足です。本書はパイプラインに1段階を加え、既存の出力を拡張します。既存の規定は廃止しません。本書に記載のない事項は PRD と HARDENING に従い、本書と矛盾する場合は安全面のルール（§5）を優先します。

先に読む箇所：PRD §5（F1〜F10）、§6、§8。HARDENING の L4、L6、L9、D5。実装は §6 の順序で進めます。原案からの変更点は §9、コードで強制するゲートは §10、調査基準 v2 の追加事項は §12、後続の作業は §13 に記載します。

## 1. 変更点

現在のコーチは、利用者が貼り付けた資料（エージェントメール、求人文、任意の履歴書）のみを材料にします。ここに自動調査の段階を加え、登録した企業ごとに、調査した企業・職種の情報と面接体験の情報も準備に使えるようにします。

- **新しいステージ R（調査）**：確認済みの企業名・職種名をもとに、構造化された**企業・職種ブリーフ**を作り、`company_context` 内に保存します。
- **スクリプト支援（F3〜F5）**：仕様は変更しません。質問の優先順位と「企業の確認ポイント」にブリーフを使います。既存のゲートはすべてそのままです。
- **面接の振り返り**：次の2種類を扱います。(a) ステージ R で集める、公開された面接体験の情報。(b) 利用者自身が面接後に記録し、企業ごとに再利用する振り返り（PRD のロードマップ項目を軽量な形で範囲に入れます）。

背景（作者の以前の転職活動で得た問題意識）：エージェント経由の中途採用では、本人の能力と関係のない理由で不採用が繰り返されることがあります。(1) エージェントの支援が不十分、または担当者によって差があり、職種や企業への理解が浅く、準備の支援も薄い場合があること。(2) 応募した職種が本人の希望と異なると、選考の後半になって初めて判明すること。候補者には、どちらも独自に確かめる手段がありませんでした。本機能はこの2点を候補者の側で補います。ステージ R はエージェントの質に左右されない調査・確認の手段となり、適合・不一致の確認（§3）は「希望した職種ではない」ことを不採用の後ではなく面接の前に示すためのものです。

## 2. ステージ R — 起動条件と入力

- 機能フラグ：サーバーの `RESEARCH_ENABLED=1`。`/api/access` が `research: true|false` を返します。オフのときは現在の動作（メール → 質問）とバイト単位で同一です。
- 流れ（既存の `profile` 再生成パターンを利用）：
  1. 最初の質問は現在と同じく表示します。
  2. 抽出した企業名・職種名を確認カードで示し、確認を求めます（修正可）。
  3. 確認後に `POST /api/research` を実行し、ブリーフカードを表示します。
  4. ブリーフを使って質問を再生成します。
- **未確認の名前は調査しません。** 抽出の誤りをそのまま検索しないためです。
- 入力は呼び出しごとに分離します。
  - 検索・抽出の呼び出し：確認した企業名・職種名、汎用語（会社概要、採用、求人、面接など）、利用者が確認カードで任意に入力した所在地と公開 URL のみ。メールとプロフィールの文面は送りません。
  - 適合判定の呼び出し（ツールなし）：検索結果に基づくブリーフ、確認済みの `company_context`、マスキング済みの利用者資料のうち判定に必要な部分（経験年数、領域、スキル）、`desired_position_profile`。
- ブリーフはセッションに保存します。再実行は明示的なボタン操作のときのみです。
- 調査の失敗でコアループを止めません。最初の質問を画面に残し、`research_status: unavailable` を表示します。

## 3. ステージ R — 収集する内容

日本語の検索を優先します。情報源の優先順位：(1) 企業の公式サイト・IR・採用ページ、(2) 信頼できる報道（直近12か月）、(3) 面接体験の公開投稿（予算が残るときのみ）。調査の順序は §12 に定めます。社員口コミサイトはサーバーでは収集しません（§12）。

以下の固定スキーマにのみ出力します。

- `company_snapshot`：法人名、事業内容、規模、設立、本社・拠点、上場・親会社、財務（会計期間付き、3件まで）、最近のニュース。全項目に出典を付けます。`self_claims` は企業自身の主張（満足度、順位、成長率、実績の誇示）で、事実の欄とは分けて表示します。
- `position_analysis`：この企業でその職種が実際に行う業務（公開されていればチーム・組織の文脈を含む）、公開された必須・歓迎スキル、年収（`min_jpy`、`max_jpy`、`fixed_overtime_hours`）、雇用形態（`kind`）、残業（`monthly_hours`）、勤務地、出社・リモートの表記、顧客先常駐の記載（`stated`）、変更の範囲。
- `source_conflicts`：出典の間で値が食い違う項目と両側の値。4ページの予算では偶然にしか見つからないため、空でも「一致した」とは表示しません。
- `interview_intelligence`：公開されている選考の段階と、報告された面接質問（短い場合は原文どおり）および各出典。公式の採用ページ以外の情報には、すべて「候補者による報告、未検証」と表示します。
- `fit_evaluation`：職種と利用者の資料との一致点・相違点。各項目は、利用者資料の事実または出典付きの企業情報のどちらかを引用します。それ以外は事実として扱わず `needs_user_confirmation[]` に入れます。
- `desired_position_profile`：利用者が実際に希望する内容。一度入力すれば企業をまたいで再利用します。希望する業務内容、除外する職種、必須条件（例：年収 700万円以上、残業 月20時間以内、特定職種を除外）。ブラウザの localStorage に専用のキーで保存し、オプション画面で編集・削除できます。送信先は適合判定の呼び出しのみです。希望条件の行ごとの照合（§12）はブラウザ内で計算し、照合のためには送信しません。目標年収、雇用形態、勤務地、リモート日数、常駐の除外、職種の種類は照合専用で、適合判定にも送りません。
- `mismatch_flags`：(a) エージェントメール・貼り付けた資料の記載、(b) 公開情報と調査が示す実際の職種、(c) `desired_position_profile` の三者比較。重要な相違をすべて示します。資料と調査の相違（例：メールは「プロダクトマネジメント」、公開された職種はデリバリー・PMO 業務）と、調査と希望の相違（例：職種は実在するが除外職種に当たる、公開求人の残業時間が希望の上限を超えている）です。各フラグは相違の両側を引用します。フラグは確認を促すものであり、エージェントの虚偽や職種の良し悪しを判定するものではありません。
- `company_checkpoints`：選考の中で確認するとよい中立的な論点（例：公開求人の残業の記載と、希望の月20時間以内（例）の確認）。結論ではなく確認の質問として書きます。`mismatch_flags` はこの一覧に反映され、条件以外の相違は F10 の逆質問にも反映されます（§4）。
- `sources[]`：`{title, url, accessed_date, retrieved_at, page_age, fetched, published_date（表示があれば）}`。使用したすべての情報源を記載します。`retrieved_at`、`page_age`、`fetched` はツールの結果からコードが設定します。`fetched` は全文の確認を意味しません。
- 調査日を保存します。

出典のない項目は `not_found` とします。中身が空でも正直なブリーフは正しい結果であり、捏造されたブリーフはリリースを止める欠陥です。

## 4. 既存機能との統合

- **F2 質問生成**：生成の文脈を `company_context + research_brief` にします。既存のゲート（10問中6問以上が資料固有の要素を参照）を拡張し、10問中3問以上が調査結果（報告された面接質問、事業・ニュース、職種の詳細）にたどれることを求めます。質問ごとに `basis: mail | research | pack` を保存します。ゲートに失敗したら1回再生成し、それでも失敗すれば利用者に表示します（現在の F2 と同じ）。
- **F3〜F5（構成、添削、模範回答）**：変更しません。ブリーフは模範回答を先に作る質問の選択と `company_checkpoints` に使えますが、模範回答に事実を加えてはいけません。模範回答は引き続き利用者の回答・添付履歴書の事実の並べ替えのみとします（HARDENING L6）。
- **F10 逆質問**：3問のうち1問以上を調査結果（最近のニュース、事業の方向性）に基づかせ、出典を示します。既存の条件質問ゲート（年収・残業・入社日など）は変更しないため、条件に関する相違は逆質問にせず、`company_checkpoints` でエージェントへの確認事項として示します。
- **面接後の振り返り**：利用者が企業セッションを開いて面接完了を記録したとき（または要求があったとき）、3項目の振り返りを提示します。実際に聞かれた質問 / 難しかった・聞き返された場面 / 結果と次の段階。企業ごとにブラウザ内に保存します。生成した質問と実際に聞かれた質問の重なりを計算して表示します。この数値はブラウザ内にのみ置きます（§9）。保存先はセッションとは別のキーで、「終了・保存」やリセットでは消えず、欄を空にする（その企業）か ⚙ の画面（すべて）で消します。AIには送りません。Markdown の書き出しには振り返りの本文だけを含め、重なりの数値は含めません。
- **UI（F7）**：ブリーフは同じ単一画面のチャットの流れの中で1枚のカードとして表示します。概要（3〜5行）、希望条件の照合、確認が必要な相違、報告された質問、口コミサイトの確認（利用者本人）、適合点、確認ポイントの順に並べ、出典は下部に折りたたみます。調査中は進行状況を示し、縮退時は `research_status` をそのまま表示します。
- **チュートリアル**：架空の企業のブリーフ（不一致フラグと希望条件の照合の例を含む）を「架空の例」と明示して表示します。AI 呼び出しは0です。

## 5. ガードレール（必須、弱めてはならない）

1. **検索のプライバシー**：検索クエリに含めるのは企業名、職種名、汎用語（会社概要、採用、求人、面接など）のみです。利用者が確認カードに入力した所在地と公開 URL は、検索・取得の入力にのみ使います。利用者の氏名、履歴書の文面、メールの内容、その他の個人識別情報は決して含めません。利用者の資料は適合判定の文脈でのみ使い、検索エンジンや取得先には送りません。
2. **ウェブの内容はデータ**：取得した内容はすべて、貼り付けられたメールと同じく信頼できないデータです（HARDENING L4）。ページ内の指示は無視します。固定のブリーフスキーマにのみ抽出し、ページの指示に従わず、取得した文章でプロンプト、ルール、採点を変更させません。
3. **捏造の禁止**：ブリーフの事実の主張にはすべて出典を付けます。単一の出典の項目には単一出典と表示します。面接の報告は体験談であると表示します。
4. **著作権**：保存するのは要約とリンクであり、ページの全文は保存しません。短い抜粋は、報告された質問の文言に必要な場合に限ります。
5. **アクセスの制限**：公開ページで、規約上自動取得が禁止されていないページのみを対象とします。PDF は取得しません。ログインが必要なページの取得、有料の壁や robots の回避、利用者のアカウントや Cookie の調査への利用は行いません。
6. **コストと再現性**：ページ取得・抽出・分類は Haiku 級、適合の統合は Sonnet 級とし、モデル ID は既存の設定1か所（`lib/claude.js` の `MODELS`）に固定します。取得は企業ごとに最大8回（検索4回 + ページ取得4回）とします。再現性はモデルの固定と JSON スキーマで確保します（§9）。
7. **既存のゲートは変更しない**：すべての処理の前に個人情報をマスキングします。添削はルール ID を引用するか除外します。採点は（質問、回答、基準）のみを見る独立した呼び出しです。不確かな場合は推測せず「要確認」を返します。

## 6. 実装順序

1. ブリーフのスキーマ、セッションへの保存、`research_status`。コアループは変更しません。
2. 検索・取得の段階（上限、キャッシュ、縮退経路、開発モードのクエリログ）。
3. チャット UI のブリーフカード表示。
4. F2 の文脈とゲートの拡張、質問ごとの `basis`。
5. 適合判定と確認ポイント。
6. 振り返りの記録と重なりの統計。

手順ごとにコミットします。DEVLOG には事実のみ（作ったもの、測定したもの）を記録します。ただし、重なりの統計は記録しません（§9）。

## 7. 受け入れ基準（測定可能）

- **正直さのテスト**：TEST-CASES ケース A の架空企業（株式会社サンプルテック（仮））でステージ R を実行します。ブリーフは `not_found` の項目を返し、捏造された情報を含みません。類似名の別企業の結果を事実に使わないことも確認します。
- **実在企業のテスト**：実装者が選ぶ上場企業1社（企業名はリポジトリに残しません）で、出典付きの概要の事実が3件以上、口コミサイトの出典が0件、`read_no_value` と `not_researched` が実際の取得結果と一致し、面接情報が「出典付きの報告質問2件以上」または「公開された報告は見つからなかった」という明示のどちらかを満たします。
- **適合のテスト**：`fit_evaluation` の一致点・相違点はすべて、利用者資料の事実または出典付きの企業情報を引用します。述べられていない仮定に基づく項目は0件です。
- **不一致のテスト**：エージェントメールがプロダクトマネジメントと記載し、公開された求人がデリバリーマネジメントと記載し、希望プロフィールがデリバリー専任の職種を除外する合成ケース（TEST-CASES ケース E）で、双方の文面を引用した `mismatch_flags` が出ます。入力に相違がなければ、フラグ0件が正しい出力です（フラグを作り出しません）。
- **照合のテスト**：`test/conditions.test.js` で、行ごとに満たす・満たさない・未確認のみを返し、合計・等級がなく、類似の求人や求人・公式以外の出典では状態が変わらないことを確認します。口コミのデータがなくても照合と `mismatch_flags` が動作します。
- **断定語・公正採用のテスト**：断定・等級の語を含む主張と、公正採用の観点で不適切な報告質問が、件数のみを残して除外されることを単体テストで確認します。件数は企業に帰属させません。
- **プライバシーのテスト**：開発モードのクエリログは個人情報を伏せて記録し、伏せた行に `redacted: true` を付けます。実際に送られた検索語に該当がないこと（`redacted: true` が0件）を確認します。加えて、検索リクエストにメール・プロフィールの文面が含まれないこと、適合判定のリクエストに `tools` キーがないことを、リクエストオブジェクトの単体テストで証明します。
- **回帰**：TEST-CASES の B・C・D は変更なく通過します。調査をオフにすると、本機能追加前の動作を再現します。
- **デモの準備**：デモ用の企業で、ブリーフと10問（`basis` 付き）が1回の流れで最後まで生成されます。

## 8. 範囲外

企業への連絡、応募、アカウント・ログインの自動化、記事全文の保存、株価・IR のリアルタイムの深掘り、JP パックの添削ルールと4段階の基準の変更。

## 10. コードゲート（モデルの主張を信用しない）

サーバーツールは Anthropic 側で実行されます。次のゲートはすべて単体テストの対象です。

1. **URL**：各出典の URL は、その応答の実際の `web_search` / `web_fetch` の結果に含まれていなければなりません。含まれなければ、その出典を除外します。
2. **主張と出典**：各主張は `source_ids` を持ちます。出典がすべて除外された主張、出典のない主張は `not_found` にします。モデルが同じ id を複数の出典に使った場合、その id の出典はすべて除外します。
3. **件数**：`source_count` と `single_source` は、モデルの値を使わず、残った出典からコードで計算します。
4. **企業の同一性**：各出典は `entity_match: exact | similar | unknown` を持ち、事実の根拠にできるのは `exact` のみです。`exact` 以外の出典を1件でも引用した主張は、別企業の数値を含むおそれがあるため `not_found` にします。架空の社名でも類似名の別企業が返ることを実呼び出しで確認したため、必須のゲートとしました。`exact` の出典が残らなければ、全項目を `not_found` とし、検索が実際に行われていれば `research_status: ok` とします（正直な空の結果）。
5. **職種の同一性**：`position_match: exact | similar | unknown`。類似の求人の条件には類似である旨を表示し、この職種の条件としては述べません。
6. **抜粋の上限**：報告された質問の文言は80文字までとし、ページの全文は保存しません。
7. **検索の成否**：検索の実施回数は `usage.server_tool_use.web_search_requests` で数えます。検索結果の `content` はエラーでも例外にならず、エラーオブジェクトとして返ります。実際の検索が0回でエラーがあれば `research_status: unavailable` とし、`not_found` にはしません。ツールの失敗を「存在しない」と示さないためです。検索が実行されていても、失敗した検索があり `exact` の出典が残らなければ同様に `unavailable` とします（§10-4 の例外）。ページ取得の失敗だけでは変更しません。類似名のページの取得失敗は日常的に起こり、架空の社名で正直な空の結果を返す §7 の基準を不安定にするためです。状態を変えない失敗の件数は、部分的な結果と分かるようコードが `tool_errors` に記録します。`pause_turn` は回数を制限して再開します。

8. **適合判定の引用**：`fit_evaluation` の一致点・相違点は、利用者資料にある引用（マスキング後の本文と照合）か、実在の出典を持つ主張にある引用のどちらかを必要とします。それ以外と、類似の求人の主張に基づくものは `needs_user_confirmation` に移します。`mismatch_flags` は、異なる2つの出どころの両側を照合できなければ除外します。`company_checkpoints` は疑問文のみ残し、調査に基づくものは実在の出典を必要とします。希望の語句や数字を含むものは `desired_profile` に付け替え、逆質問に渡しません（言い換えはコードでは検出できません）。

9. **口コミの出典**：`source_type: review_site` の出典は URL と同一性が正しくても除外し、それを引用した主張は `not_found` にします。`blocked_domains` だけでは転載ページを防げないためです。
10. **未確認の区別**：`not_found` には `unknown_kind` を付けます。引用したページを実際に取得できていれば `read_no_value`（読んだ範囲で見つからない）、検索のみ・取得失敗・予算切れ・引用なしは `not_researched`（今回は未調査）です。どちらも「存在しない」とは表示しません。読んだページは `checked_source_ids` に残し、根拠としては数えません。
11. **数字の照合**：`min_jpy`、`max_jpy`、`fixed_overtime_hours`、`monthly_hours` は、主張の本文に現れる値のみ残します（万の単位とカンマを正規化）。それ以外は `null` で、未確認になります。
12. **断定語と公正採用**：パックの `banned_terms` を含む主張は除外し、`banned_removed` に件数のみ残します。`fair_hiring_patterns` に一致する報告質問は除外し、`fair_hiring_removed` に件数のみ残して、一般的な案内を1件だけ表示します。
13. **調査の範囲**：`coverage` は検索・取得の回数、成否、上限到達（`budget_exhausted`）をコードが数えます。
14. **URL の入力**：所在地と URL は任意です。http(s) のみ、認証情報なし、250文字以内、連絡先のパターンを含まないものだけを受け付けます。

レート制限：キー `research:<ip>`、10分あたり5回。アクセスコードの確認は他の API と同じです。`vercel.json` の `functions` で `api/research.js` の `maxDuration` を 120 とします。

## 11. ルール（作者の過去の調査から）

作者が以前の転職活動で企業を調べた際の知見です。スキーマとプロンプトのルールとしてのみ使います。

- 主張ごとに確信度 `high | medium | unknown` を付けます。
- 業界平均を企業のスコアとして扱いません。
- 希望条件の行ごとの照合は判定ではありません。企業単位の合計、点数、並べ替え、色分けは作りません。
- 記載なし、掲載なし、認定なしは、どの方向の信号にも使いません。確認の方法のみ示します。
- 年収の範囲は保証ではありません。賞与・残業代が含まれるかを記載し、不明なら不明と表示します。
- 事業形態の事実（自社製品 / 受託 / 常駐 / 派遣の許可）は報告しますが、個々の職種の法的な契約形態は断定しません。
- 不明な項目は確認の質問にします。
- 調査日を保存します。
- 判定のフィールドは一切設けません（推奨 / 非推奨など）。
- 不一致フラグは確認を促すものであり、必ず両側を引用します。
- 報告された質問は、公式の採用ページに由来するものを除き、常に「候補者による報告、未検証」と表示します。

**口コミサイト**：サーバーは収集しません。カードにはサイトへのリンク（トップページのみ。企業名を URL に含めません）と、利用者本人のメモ（サイト、閲覧日、表示されたサンプル数、本人の要約）を置きます。メモはブラウザの専用キーに保存し、「投稿者の主観、未検証」と表示します。AI にも書き出しにも渡さず、固定の開かれた確認質問を1件表示する条件としてのみ使います。本文の貼り付けは警告します。

**希望条件の照合**：`public/conditions.js` の純粋関数がブラウザ内で計算し、行ごとに `met`、`unmet`、`unknown` のみを返します。状態を変えられるのは公式と求人の出典のみで、`position_match` が `exact` でなければ常に未確認です。リモート日数は表記が頻度を保証しないため常に未確認です。面接後に利用者が状態を選んで記録した回答（話した方の役職、日付、書面の有無）は求人の値より優先します。照合の行は書き出しに含めません。

**確認質問のひな形**：`packs/jp.json` の `research.checkpoint_templates` を相手別（エージェント、人事、現場の管理職、決裁者・役員）に、AI を呼ばずに表示します。状態が確定した軸の質問は出しません。

**訂正の経路**：カードの各項目に非表示のボタンを置きます。非表示にした項目は以後のリクエストと書き出しから除かれます。調査日からの経過日数を表示します。ご連絡は README に記載の Issues で受け付けます。

**実呼び出しで確認する事項**：拡張したスキーマが API の文法の上限に収まるか、null を許す整数の扱い、Haiku が順序に従うか。上限を超える場合は `work_style`、`change_scope`、`financials`、`client_site_work` の順に外します。
