## 1. 목적
- 면접 코치의 **면접 답변 코칭을 더 깊게** 하는, 근거 있는 규칙 데이터를 만든다.
- 채용 전 과정(서류·内定·在留)은 "면접 답변에서 언급될 때 코치가 알아야 할 전제"로 다룬다.
- **서류는 면접 연결형만**(사용자 결정): 職務経歴書의 실적을 면접 답변(基準・数字)과 自己紹介로 바꾸는 규칙, 履歴書는 厚労省 様式例(2021) 기준 점검까지만. 서류 작성·첨삭 단독 기능의 재료가 아니다. 대회 회피 목록의 "AI 이력서"와 거리를 둔다.
- 모든 규칙은 출처가 달린 요약·규칙으로만 존재한다. 원문 전재는 하지 않는다.

### 2.2 출신 선택 메커니즘 (확정)
- MVP에서 출신은 입력받지도, 자동 감지하지도 않는다. 출신은 팩의 `language_pair.native`로 결정된다(`ko` → C2).
- 이력서·메일에서 국적을 추론하는 기능은 스테레오타입 방지 원칙·개인정보 비저장 원칙과 충돌하므로 채택하지 않는다.

## 3. 데이터 권리 정책
- **공적 출처**: 이용약관을 직접 열어 `PDL1.0`, `政府標準利用規約(第2.0版)`, `CC BY 4.0` 중 하나임을 확인하고 `terms_url`과 출처 표기(예: `出典：厚生労働省ホームページ (URL)`)를 기록한 것만 `kind: public`으로 쓴다. JETRO처럼 사전 허가제인 출처는 허가 확인 전까지 쓰지 않는다. ハローワーク 求人情報는 목적 외 이용 금지이므로 쓰지 않는다.
- **민간 출처**: 사실·관행 요약과 우리가 새로 쓴 예문만 허용한다. **전재 판정은 기계적으로 한다**: 일본어·한국어 20자 이상 또는 영어 15단어 이상이 원문과 연속 일치하면 기각한다.
- **SNS 실패 사례(사용자 결정)**: insane-search 수집은 **내부 리서치에만** 쓴다. 레포에는 원문·URL·개인 사례를 넣지 않는다. 여러 출처에서 반복된 실패 패턴만 우리가 새로 쓴 문장으로 넣는다. X는 omo CLI 경로를 쓰지 않고 직접 수집한다(DEVLOG 11/02 메모리 사고).
- **공정 채용 규범 앵커(필수)**: T3·T4의 일본 측 기술은 厚生労働省「公正な採用選考の基本」과 履歴書 様式例(2021)를 1차 기준으로 삼는다. 민간 관행 서술이 이와 충돌하면 공적 규범을 우선한다.
- **스테레오타입 방지**: 출신 노트는 `confidence: high`만 채택한다. 노트마다 ① 치환 테스트(출신을 바꿔도 참이면 출신 규칙이 아니라 공통 규칙) ② 결손 테스트(후보자의 부족·미숙을 함의하면 기각)를 기록한다. 스테레오타입 관점은 **단독 거부권**을 가진다.

## 4. 산출물 (전부 `01_설계문서/research/` 아래)
1. 조사 문서(한국어, 사실 서술마다 `claims.json` id 각주)
2. `VERIFICATION-LOG.md`: 채택·기각·보류와 그 이유
3. `jp-draft-v2.json`: **`packs/` 밖에 둔다**(packs는 Vercel 번들·공개 레포 대상). `packs/`·`lib/`·`api/`·`public/`·`test/`는 생성·수정을 금지한다.
4. `validate-draft.mjs`: 단독 실행 스크립트. `npm test`와 연결하지 않는다.
5. `SUMMARY.md`: 채택 규칙 수, 미확인 칸, 제품 반영 제안
6. `README-SECTION.md`: 데이터 출처·라이선스, 그리고 "본인 노하우(규칙 데이터)와 외부 데이터"의 구분

### 4.1 통합 계약 (이 계약에 맞지 않는 규칙은 팩 후보가 아니다)
- `jp-draft-v2.json`은 `packs/jp.json`과 **같은 최상위 키**만 가진다. 추가 가능한 것은 3종이다.
  1. `correction_rules[]`: 기존 7필드(`id, type, pattern, replacement, reason, example_before, example_after`). T4 또는 C2에서 "말한 문장"에 대한 修正前→修正後가 성립하는 것만 넣는다.
  2. `culture_notes[]`: 일본어 문장(프롬프트 주입용)
  3. `question_taxonomy.stages/categories` enum append(예: `二次面接`, `カジュアル面談`)
- 주입 문자열은 일본어(`*_ja`)로 쓴다. 한국어(`*_ko`)는 문서·UI 설명 전용이다.
- **주입 예산**: 승인 병합 1회당 `correction_rules` +3건, `culture_notes` +5건, 합계 +1,000자 이내. 초과분은 다음 병합으로 넘긴다.
- 병합은 사람이 승인한 뒤에만 한다.

## 6. 실행 설계
- **동시 에이전트 10개 이하**(사용자 지시). 조사 에이전트는 R1 유닛 5개(C2, T4, T2b, T5, T2a)다.
- **검증(압축형, 사용자 결정)**: 항목마다 ① 개인정보·권리 검사는 필수로 하고, 스크립트(denylist·전재) 다음에 에이전트 1회를 돌린다. ② 근거·제품 적합성은 1회로 합친다. ③ 스테레오타입은 단독 거부권을 가진다. 반박 라운드는 blocking 지적에만 둔다.
- **통합**: 1개 에이전트. 완전성 비평 1개는 지적만 한다. 재조사는 채택 규칙이 3개 미만인 T 문서 1개당 1회로 제한한다.

## 8. 리스크
- 출처 차단 → 공적 도메인 외에는 우회하지 않고 "미확인"으로 둔다(SNS 내부 리서치는 §3 예외)
- 출신 편향 → §3 거부권, R1은 C2만
- **비용**: 직전 검증 워크플로 2개가 약 390만 토큰을 쓰고 5시간 한도를 소진했다. 실행 전 파일럿(유닛 1개)으로 토큰을 실측하고, 상한 = 실측 × 유닛 수 × 1.5로 정한다. 파일럿이 150만 토큰을 넘거나 출처 절반 이상의 페치가 실패하면 설계를 재검토한다.
- 중단 내성: 에이전트마다 결과를 파일로 즉시 저장한다(한도 중단 시 재사용).
