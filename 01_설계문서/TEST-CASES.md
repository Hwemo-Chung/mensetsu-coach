# 테스트 케이스 — 가상 데이터 세트

주의: 아래 기업·인물·메일은 **테스트용으로 작성한 가상 데이터**다. 실제 기업명과 개인정보를 쓰지 않기 위한 것이며, 데모 영상에도 이 세트를 쓴다.
기대 결과의 근거: 사용자 본인의 실제 교정 기록 문서 (business_japanese_corrections_1022.md)의 규칙 패턴 — ①질문과 어긋난 답변 ②〜の形 남용 ③ちゃんと·なんか 등 모호 표현 ④반론형 응답. "규칙에 없는 첨삭은 하지 않는다"가 원칙이므로, 기대 결과는 전부 이 규칙 범위 안에서만 적는다.

## 케이스 A — 기업 등록·질문 생성
입력 (가상 에이전트 메일, 발췌):
> 株式会社サンプルテック（仮）/ プロダクトエンジニア募集のご案内
> 業務内容：自社SaaSのプロダクト開発における要件定義〜リリース推進、PdM・デザイナーとの協業
> 必須：Webサービスの開発・運用経験5年以上、ステークホルダー調整経験
> 歓迎：BtoB SaaS経験、英語での業務対応
> 想定年収：700万円〜900万円 / 勤務地：東京（週2リモート可）

기대 결과:
- 기업 컨텍스트 추출: 포지션, 필수/우대 조건, 근무 조건이 분리되어 저장될 것
- 예상 질문 10개가 카테고리별(경험 확인 / 조정·협업 / 기술 판단 / 지망 동기)로 생성될 것
- 질문이 메일의 조건(ステークホルダー 조정, BtoB SaaS)과 연결될 것 — 일반론 질문만 나오면 실패

## 케이스 B — 질문과 어긋난 답변 (구조 코칭)
질문: 「前職で最も大変だったことは何ですか？」
답변 (일부러 어긋나게 작성):
> 「はい、前職では新しいシステムの導入を担当しまして、チームのメンバーと協力しながら進めることができました。結果として、業務の効率が上がりまして、評価もいただきました。」
(질문은 "가장 힘들었던 것"인데, 준비한 성과 사례를 말하고 있음 — 사용자의 실제 실패 유형)

기대 결과:
- 구조 점검에서 **"질문에 답하고 있지 않음"** 을 첫 번째로 지적할 것 (힘들었던 점이 답변에 없음)
- 4문형(復唱→結論→基準·数字→選択肢） 기준으로 빠진 요소를 특정할 것
- 모범답안: 힘들었던 일을 결론으로 먼저 제시하는 60초 분량으로 재작성될 것

## 케이스 C — 군더더기·모호 표현 (첨삭)
질문: 「プロジェクトの進め方を教えてください。」
답변 (일부러 규칙 위반을 넣어 작성):
> 「自分的には、まず現状をちゃんと確認する形で進めまして、なんか問題があれば、その形で対応するという形になります。ちょっと様子を見ながら、ちゃんと進めていく形です。」

기대 결과 (전부 교정 규칙 근거):
- 〜の形 남용 → 삭제하고 구체 동사로 (확인する形で → 確認し)
- ちゃんと → 구체 행동으로 치환
- なんか/ちょっと → 삭제
- 自分的には → 私としては (11/02 정정: 원 교정 기록의 규칙은 「自分的には」이고 「私的には」 규칙은 없음. 규칙 DB 밖 첨삭 금지 원칙에 맞춰 입력을 규칙과 일치시킴)
- 첨삭은 before/after + 이유 형식으로, 규칙에 없는 지적은 나오지 않을 것

## 케이스 D — 압박·반론 상황 (구조)
질문 (면접관의 반론): 「それはウチのやり方とは違いますね。」
답변 (일부러 반론형으로 작성):
> 「いえ、それは違います。私の経験では、その方法が一番効率的でした。」

기대 결과:
- 반론이 아닌 **인정 → 목적 분리 → 적용 시점 제시** 구조로 교정될 것 (교정 문서의 실제 패턴)
- 상대 방식을 부정하지 않는 모범답안이 나올 것

## 합격 기준 (케이스 공통)
- 출력 3종(구조 점검 / 첨삭 / 모범답안)이 분리되어 나올 것
- 모범답안은 일본어 + 읽기(발음) + 한국어 대역의 3단 포맷일 것
- 규칙 밖의 첨삭·없는 사실의 생성이 없을 것
