## ケースA — 企業登録・質問生成

> 業務内容：自社SaaSのプロダクト開発における要件定義〜リリース推進、PdM・デザイナーとの協業
> 必須：Webサービスの開発・運用経験5年以上、ステークホルダー調整経験
> 歓迎：BtoB SaaS経験、英語での業務対応
> 想定年収：700万円〜900万円 / 勤務地：東京（週2リモート可）

期待結果:
- 企業コンテキストの抽出: ポジション、必須/歓迎条件、勤務条件が分離して保存されること
- 想定質問10問がカテゴリ別（経験の確認 / 調整・協業 / 技術判断 / 志望動機）に生成されること
- 質問がメールの条件（ステークホルダー調整、BtoB SaaS）と結びついていること — 一般論の質問しか出なければ失敗

## ケースB — 質問とずれた回答（構成コーチング）
質問: 「前職で最も大変だったことは何ですか？」
回答（わざとずらして作成）:
> 「はい、前職では新しいシステムの導入を担当しまして、チームのメンバーと協力しながら進めることができました。結果として、業務の効率が上がりまして、評価もいただきました。」
（質問は「最も大変だったこと」なのに、準備した成果事例を話している — 作者の実際の失敗パターン）

期待結果:
- 構成チェックで**「質問に答えていない」**を最初に指摘すること（大変だった点が回答にない）
- 4文型（復唱→結論→基準・数字→選択肢）の基準で、欠けている要素を特定すること
- 模範スクリプト: 大変だったことを結論として先に示す60秒分の内容に書き直されること

## ケースC — 冗長・曖昧な表現（添削）
質問: 「プロジェクトの進め方を教えてください。」
回答（わざとルール違反を入れて作成）:
> 「自分的には、まず現状をちゃんと確認する形で進めまして、なんか問題があれば、その形で対応するという形になります。ちょっと様子を見ながら、ちゃんと進めていく形です。」

期待結果（すべて添削ルールが根拠）:
- 〜の形の多用 → 削除して具体的な動詞に（確認する形で → 確認し）
- ちゃんと → 具体的な行動に置換
- なんか/ちょっと → 削除
- 自分的には → 私としては（11/02 訂正: 元の添削記録のルールは「自分的には」で、「私的には」のルールはありません。ルールDB外の添削禁止の原則に合わせ、入力をルールと一致させました）
- 添削は before/after + 理由の形式で、ルールにない指摘が出ないこと

## ケースD — 圧迫・反論の場面（構成）
質問（面接官の反論）: 「それはウチのやり方とは違いますね。」
回答（わざと反論型で作成）:
> 「いえ、それは違います。私の経験では、その方法が一番効率的でした。」

期待結果:
- 反論ではなく**認める → 目的を分ける → 適用する場面を示す**構成に添削されること（添削文書の実際のパターン）
- 相手のやり方を否定しない模範スクリプトが出ること

## 合格基準（ケース共通）
- 出力3種（構成チェック / 添削 / 模範スクリプト）が分離して出ること
- 模範スクリプトは日本語 + 読み（発音）+ 韓国語の対訳の3段フォーマットであること
- ルール外の添削・存在しない事実の生成がないこと
